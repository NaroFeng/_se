測試架構與案例說明

本專案以「三層金字塔」構建自動化測試：最上層 E2E 驗證使用者旅程、中層 Web API 驗證 HTTP 合約與資料持久化、最下層 Unit 鎖定純業務規則。 每一層都有明確的測試邊界，愈上層愈昂貴、愈慢、但涵蓋面愈廣；愈下層愈輕快、執行愈快、錯誤回饋愈精準。

1. 測試金字塔架構

每一層標示三件事：測試邊界（測到哪裡為止）、是否依賴 DB / 網路（決定執行速度與穩定度）、 以及防護目標（這層擋下什麼類型的缺陷）。

Layer 3 E2E tests/test_e2e.py

測試邊界
從瀏覽器網址列輸入到畫面重新渲染的完整使用者旅程：開首頁 → 填 6 個欄位 → 上傳圖片 → 送出 → 卡片動態出現 → 導航到測試文件頁。只驗證「使用者看得到的結果」，不檢查 DB 內部狀態。
依賴 DB / 網路
兩者都依賴：需要真實的 uvicorn HTTP Server + 真實 SQLite 檔案（放在 pytest 的 tmp_path_factory 下）。網路僅限 localhost，不連外。Chromium 由 Playwright 啟動。
防護目標
防護「前後端契約斷裂」：表單欄位名稱改錯、JS fetch 網址寫錯、卡片未渲染、導覽連結壞掉。這類問題單元測試與 API 測試都抓不到。
執行成本
最高（秒級），因此只保留 9 個關鍵旅程案例，數量最少、位於金字塔最尖端。

Layer 2 Web API tests/test_api.py

測試邊界
從 POST /api/submissions 的 multipart 請求進入 FastAPI，經過表單解析 → validators 驗證 → 檔案落地 → SQLite 寫入，直到 HTTP 回應（狀態碼 + JSON body）為止。以 TestClient 呼叫，無需佔用真實 TCP 埠。
依賴 DB / 網路
依賴 真實 DB（但不是正式環境的 data/resume.db，而是 fixture 傳入的 tmp_path 資料庫）；不依賴外部網路（TestClient 走 ASGI in-process，無 socket）。
防護目標
防護 HTTP 合約與資料層錯誤：狀態碼錯（400 應為 422）、驗證漏接、圖片沒落地、欄位沒寫進 DB、排序錯誤、惡意副檔名被放行。
執行成本
中等（毫秒級），共 21 個測試函式，專注於「請求 → 回應」這個契約邊界。

Layer 1 Unit tests/test_unit.py

測試邊界
只測 app/validators.py 的純函式：輸入字串 / 整數 → 輸出布林值或檔名字串。完全不碰 FastAPI、資料庫、檔案系統與網路。
依賴 DB / 網路
完全不依賴 DB 與網路。只需 import app.validators，整個測試檔可在毫秒內跑完，是最快速的一層。
防護目標
防護業務規則被改錯：Email 正則放行垃圾字串、年資邊界（0 / 50）判定錯、副檔名白名單被繞過、檔名未做 UUID 化而造成路徑穿越。
執行成本
最低（毫秒級），共 13 個測試函式（參數化後展開為 67 個案例），是金字塔的基石，也是回歸測試最常跑的一層。

2. 互動式測試控制台 (Interactive Test Console)

不用離開瀏覽器就能驗證這套系統：下方提供一鍵複製指令（把精確的 pytest 指令貼到你的終端機） 與網頁即時測試執行器（直接在頁面上點擊按鈕執行測試並即時觀看輸出）。

2.1 Terminal 快速指令中心

全部指令皆使用 python -m pytest 前綴，避免多版本 Python 造成的套件版本衝突。 點擊右上角「複製指令」即可貼到終端機執行。

▶ 執行全部測試

一次跑完 Unit、Web API、E2E 三層共 97 個測試案例，適合提交前的完整回歸。

python -m pytest -v

⚡ 僅跑單元測試

只測 app/validators.py 的純函式，不碰 DB 與網路，數毫秒完成，是回歸測試最常跑的一層。

python -m pytest tests/test_unit.py -v

🌐 僅跑 API 測試

用 FastAPI TestClient 驗證 HTTP 合約、狀態碼與資料持久化，走 ASGI in-process 不佔用真實 TCP 埠。

python -m pytest tests/test_api.py -v

👁️ 有頭慢動作觀看 E2E 自動填表

你的桌面會真的彈出 Chromium 視窗，以 500 毫秒慢動作親眼看到瀏覽器自動填表、上傳圖片、 送出並更新卡片列表，然後自動導航到本頁。 

python -m pytest tests/test_e2e.py --headed --slowmo 500 -v

🔍 開啟 Playwright Trace Viewer

先用 --tracing=retain-on-failure 在測試失敗時保留 trace（DOM snapshot、網路請求、截圖）， 再開啟 Trace Viewer 就能像看影片一樣逐步回放，失敗時特別好用。 （--tracing=on 則是每次都保留，成功時較吃磁碟。） 

python -m pytest tests/test_e2e.py --tracing=retain-on-failure -v
python -m playwright show-trace test-results/

🎯 只重跑上次失敗的案例

配合 --lf（last-failed）只重跑上次失敗的案例，並用 -x 在第一個錯誤就停下、 --tb=long 印出完整堆疊。開發節奏最好用的一條。 

python -m pytest --lf -x --tb=long

2.2 網頁即時測試執行器 (Live Web Runner)

直接在頁面上按按鈕執行測試，結果會像終端機一樣完整印在下方。 執行過程中伺服器會在背景開一個 python -m pytest 子行程，並把它的資料庫與上傳目錄指向一次性暫存資料夾， 因此不會污染正式的 data/resume.db 與 uploads/。

3.1 Unit — tests/test_unit.py

      

        

          
            
測試函式測試輸入 (Input)預期輸出 (Expected)背後驗證邏輯

          
          
            

              test_validate_email_accepts_valid_addresses
              user@example.com、first.last@example.co.uk、user+tag@example.com、user_name@example-domain.com、USER@EXAMPLE.COM、a@b.co
              全部 True
              參數化測試（Happy Path）。確認正則可接受本地部分的多種合法字元（. _ % + -）、多層網域、大寫字母，以及最短的合法網域。
            

            

              test_validate_email_rejects_invalid_addresses
              ""、plainstring、no-at-sign.com、user@、@example.com、user@example、user @example.com、user@exam ple.com、user@@example.com、user@example.com.、user@.com、user@example.c、None、12345
              全部 False
              Edge Cases。涵蓋缺 @、多 @、含空白、TLD 少於 2 碼、空網域標籤、型別錯誤。None / 12345 用來確認函式不會拋例外。
            

            

              test_validate_experience_accepts_range_boundaries
              0、1、25、49、50
              全部 True
              邊界測試。0 與 50 為規格定義的合法上下界（inclusive），這兩個值若被寫成 < / > 就會造成合法履歷被拒。
            

            

              test_validate_experience_rejects_out_of_range_values
              -1、-100、51、1000、99999
              全部 False
              負數年資（業務上不可能）與超過 50 年（資料溢位風險）都必須被擋下，並由 API 層轉成 HTTP 400。
            

            

              test_validate_experience_rejects_non_integer_values
              "3"、3.5、None、True、False、[3]
              全部 False
              型別安全。刻意排除 bool（bool 是 int 的子類別，True 會變成 1 而混進來）；字串與浮點數也拒絕，避免 "3"、3.5 年混進來。
            

            

              test_validate_experience_boundaries_match_specification
              MIN_EXPERIENCE、MAX_EXPERIENCE 常數
              (0, 50)
              「規格守護」測試。直接斷言常數本身符合需求文件，避免日後有人調整常數卻忘記更新對應的測試與文件。
            

            

              test_validate_image_extension_accepts_allowed_extensions
              photo.jpg、photo.jpeg、photo.png、photo.webp、PHOTO.JPG、a.b.png、"  spaced.png  "
              全部 True
              白名單命中。副檔名取「最後一個」且轉小寫比對，因此 PHOTO.JPG、多點的 a.b.png 與前後有空白的檔名都要能通過。
            

            

              test_validate_image_extension_rejects_disallowed_extensions
              virus.exe、script.sh、doc.pdf、archive.zip、noextension、photo.jpg.exe、photo.svg、""、None、123
              全部 False
              惡意檔案攔截。photo.jpg.exe 是典型的雙副檔名繞過手法（真正副檔名是 .exe），必須以最後一段為準來判定。
            

            

              test_validate_image_extension_allowed_set
              ALLOWED_IMAGE_EXTENSIONS 常數
              恰為 {.jpg, .jpeg, .png, .webp}
              白名單防護：確保沒有人未經檢討就把 .svg / .gif 等可攜 Script 的格式加進去。
            

            

              test_generate_safe_filename_preserves_extension
              photo.png、photo.JPG、a.b.jpeg、photo.webp、noext
              副檔名分別為 .png、.jpg、.jpeg、.webp、.bin
              確認「保留原副檔名」的語意：副檔名被轉小寫保留，原始檔名主體則被 UUID4 取代；沒有副檔名時以 .bin 兜底。
            

            

              test_generate_safe_filename_is_unique_per_call
              同一個 photo.png 連續呼叫 2 次
              兩次結果不同，皆符合 [0-9a-f]{32}\.png
              UUID4 唯一性保證不同使用者上傳同名檔案時不會互相覆蓋，是檔案落地策略的核心保證。
            

            

              test_generate_safe_filename_removes_directory_components
              ../../etc/passwd.png、C:\\Windows\\System32\\evil.exe、/etc/shadow.jpg
              結果只剩 <uuid>.<原副檔名>，不含任何目錄分隔字元
              路徑穿越防護。原始檔名的主體被完全替換掉，所以 ../ 片段自然失效——這是「白名單副檔名 + UUID 檔名」雙重防線的第二道。
            

            

              test_generate_safe_filename_handles_empty_input
              ""、None
              皆回傳符合 [0-9a-f]{32}\.bin 的檔名
              防禦性程式設計：空值輸入不得拋出例外（避免 500），而是以 .bin 安全兜底。
            

          
        

      


      
3.2 Web API — tests/test_api.py

      

        

          
            
測試函式測試輸入 (Input)預期輸出 (Expected)背後驗證邏輯

          
          
            

              test_create_submission_returns_201_and_persists_record
              完整 multipart：name、email、role、experience_years=3、bio、avatar（io.BytesIO 假 PNG）
              HTTP 201；JSON 含 id、name、avatar_path、created_at
              Happy Path。驗證 201 Created 的回應內容與實際寫入 DB 的列一致，確保 avatar_path 是相對於網站根目錄的路徑（uploads/<uuid>.png）。
            

            

              test_create_submission_persists_record_into_database
              送出一次合法表單後，直接讀取沙盒資料庫
              資料表內有 1 筆，且 name 與 experience_years=3 正確
              「真的 commit 了嗎」？POST 回 201 只能證明 API 願意回應，這個案例直接對 DB 下 SQL 驗證持久化。
            

            

              test_create_submission_saves_avatar_into_upload_dir
              同上，另指定 tmp_path 當作 upload 目錄
              uploads/ 內確實存在檔案，內容位元組與上傳內容相同
              確認「檔案真的落地」而不只是 DB 有紀錄。檔名為 UUID，故不會覆蓋既有檔案。
            

            

              test_create_submission_generates_unique_filenames
              連續 POST 兩筆，兩者使用相同檔名 avatar.png
              兩筆 avatar_path 不同，且 uploads/ 內有 2 個檔案
              驗證 UUID4 檔名策略的實際效益：使用者上傳同名檔案時不會互相覆蓋。
            

            

              test_create_submission_rejects_invalid_email
              email = "not-an-email"，其餘欄位合法
              HTTP 400；detail 含「電子郵件」
              驗證 API 層確實呼叫了 validators.validate_email()，且失敗時回傳 400（規格指定）而非 422。
            

            

              test_create_submission_rejects_out_of_range_experience
              experience_years = -1 與 51
              HTTP 400；detail 含「年資」
              同一條規則的兩個方向（負數與超上限）都要被擋下，並且不會有任何資料寫進 DB。
            

            

              test_create_submission_rejects_executable_file_extension
              avatar 檔名為 malware.exe，內容偽裝成 PNG
              HTTP 400；detail 含「僅允許」
              「惡意檔案」測試。重點是看副檔名而不是看檔頭 magic bytes，因此偽裝內容也無效；同時驗證該檔案不會被寫進 uploads/。
            

            

              test_create_submission_rejects_blank_name
              name = "   "（只有空白）
              HTTP 400；detail 含「姓名」
              邊界值。空字串在瀏覽器端可能被 required 擋下，但 API 可能被 curl 直接呼叫，因此伺服器端仍需驗證。
            

            

              test_create_submission_rejects_blank_role
              role = "   "（只有空白）
              HTTP 400；detail 含「職位」
              與姓名相同的防呆規則，確保兩個必填欄位的處理一致。
            

            

              test_create_submission_treats_empty_string_as_missing_field
              name = ""（完全空字串）
              HTTP 422
              釐清兩種失敗語意：未提供（空字串）由框架回 422，提供了但內容無效（空白、格式錯）由業務層回 400。
            

            

              test_create_submission_requires_avatar_file
              完全不帶 avatar 欄位
              HTTP 422
              表單層級的必要欄位缺失交由 FastAPI/Pydantic 處理（422），與「格式錯誤但有值」的 400 區分開來，確保兩種失敗語意各自清晰。
            

            

              test_list_submissions_returns_empty_list_when_no_records
              全新的空白測試資料庫
              HTTP 200；body 為 []
              確認沒有資料時回傳空陣列而非 null 或 404，前端才能直接 forEach 渲染。
            

            

              test_list_submissions_returns_records_ordered_by_newest_first
              連續 POST 兩筆（甲、乙）
              HTTP 200；陣列第一筆是乙、第二筆是甲
              排序契約。ORDER BY id DESC 讓新提交永遠出現在列表最上方，讓首頁的卡片體驗符合直覺。
            

            

              test_submit_then_list_returns_the_new_record
              先 POST 一筆，再 GET /api/submissions
              GET 回傳陣列長度為 1，且 name 與 POST 的輸入一致
              端到端的 API 回合驗證（限 API 層）：確認 POST 有真的 commit 到 DB，而不是只寫在記憶體。
            

            

              test_index_page_is_served
              GET /
              HTTP 200；回應內容含 survey-form
              路由層的 smoke test：確認首頁靜態檔案被正確掛載，且回傳的是表單頁而不是 404。
            

            

              test_test_docs_page_is_served
              GET /test-docs
              HTTP 200；回應內容含「測試架構與案例說明」
              確認第二個頁面的路由與檔案命名都正確，避免導覽列連結到空白頁。
            

            

              test_run_tests_executes_unit_suite
              POST /api/run-tests，body {"suite": "unit"}
              HTTP 200；returncode == 0、passed == true、stdout 含「passed」
              互動式控制台的核心驗證。刻意只跑最輕的 Unit 套件（約 1 秒），證明端點真的會啟動 pytest 子行程，卻不會拖慢整個測試流程。
            

            

              test_run_tests_does_not_pollute_production_storage
              執行一次 {"suite": "unit"} 後檢查沙盒 DB 與上傳目錄
              上傳目錄為空、資料表 0 筆
              最關鍵的防呆：測試執行器必須把子行程的 RESUME_DB_PATH / RESUME_UPLOAD_DIR 指向一次性暫存資料夾，絕對不能寫入正式的 data/resume.db 與 uploads/。
            

            

              test_run_tests_rejects_unknown_suite
              body {"suite": "not-a-suite"}
              HTTP 422
              套件名稱以 Literal 型別限定，只接受 unit/api/e2e/e2e_headed/all，任何其他值直接被框架擋下，無法拼出任意指令。
            

            

              test_run_tests_suite_mapping_is_complete
              直接檢查 TEST_SUITE_ARGS 常數
              五個 suite 的 pytest 參數完全符合規格
              純資料斷言，不實際執行。特別驗證 e2e_headed 必須帶上 --headed --slowmo 500 兩個選項，否則網頁按鈕就不會真的彈出 Chromium。
            

            

              test_run_tests_rejects_nested_execution
              先設好環境變數 RESUME_RUN_TESTS_ACTIVE=1 再呼叫端點
              HTTP 409；detail 含「巢狀」
              防止無限遞迴的最後一道防線：若目前行程本身就是被 /api/run-tests 啟動的子行程，就拒絕再跑一次，否則「執行全部測試」會變成測試→測試→測試的無盡循環。
            

          
        

      


      
3.3 E2E — tests/test_e2e.py

      

        

          
            
測試函式測試輸入 (Input)預期輸出 (Expected)背後驗證邏輯

          
          
            

              test_home_page_renders_form_fields
              開啟 GET /
              表單 6 個欄位（name / email / role / experience / bio / avatar）、送出按鈕與列表容器皆可見；計數文字與卡片數量一致
              旅程起點。先確認頁面本身有渲染，才有意義去測後續互動；這是「先確認插座有電」的 smoke check。
            

            

              test_submit_form_inserts_new_card_into_list

        為什麼 API 測試要用「獨立的測試 DB」與「Mock 圖片」？

        ① 避免污染正式資料：正式環境的 data/resume.db 與 uploads/ 是使用者資料。若測試直接寫入，會造成資料錯亂，而且測試結果會受既有資料影響而不可重現。因此 conftest.py 以 fixture 傳入 tmp_path 底下的資料庫與上傳目錄，每個測試案例都是全新且互不干擾的沙盒。

        ② 避免依賴真實檔案：Mock 圖片用 io.BytesIO 與 zlib 產生合法的 PNG 位元組，不需要在 repo 內放二進位測試素材，測試檔保持純文字、可 diff、也方便閱讀。

        ③ 避免依賴外部網路：TestClient 走 ASGI in-process 呼叫，localhost 以外一律不連；E2E 也只啟動本機 uvicorn。因此整套測試可離線、可重複、無副作用地執行。
      

    


    
    

      
4. 執行指南

      
在專案根目錄（resume-survey-app/）下開啟終端機，依需求選擇要執行哪一層測試。


      

        

          
安裝依賴

          
$ python -m pip install -r requirements.txt
$ python -m playwright install chromium

        

        

          
啟動本機服務（選用）

          
$ python -m uvicorn app.main:app --reload
# http://127.0.0.1:8000

        

      


      
4.1 一次跑完三層測試

      
$ python -m pytest -v


      
4.2 分層執行

      
# Layer 1 — Unit（最快，數毫秒）
$ python -m pytest tests/test_unit.py -v

# Layer 2 — Web API（毫秒級）
$ python -m pytest tests/test_api.py -v

# Layer 3 — E2E（秒級，需 Chromium）
$ python -m pytest tests/test_e2e.py -v

# Layer 3 — 有頭慢動作（桌面會彈出 Chromium 視窗）
$ python -m pytest tests/test_e2e.py --headed --slowmo 500 -v


      
4.3 常用組合

      
# 只跑單元 + API（CI 的快速守門）
$ python -m pytest tests/test_unit.py tests/test_api.py -v

# 只跑某個測試函式
$ python -m pytest tests/test_unit.py::test_validate_email_rejects_invalid_addresses -v

# 顯示 print 與失敗細節
$ python -m pytest -vv -s --tb=short

# 只重跑上次失敗的案例
$ python -m pytest --lf -x --tb=long

# 產生覆蓋率報告
$ python -m pytest --cov=app --cov-report=term-missing


      
4.4 測試隔離說明

      
# conftest.py 透過 tmp_path / tmp_path_factory 建立沙盒，
# 測試期間完全不會碰到正式環境的 data/resume.db 與 uploads/。
#
#   db_path    -> tmp_path / "data" / "resume.db"
#   upload_dir -> tmp_path / "uploads"
#   E2E server -> tmp_path_factory 底下的獨立 uvicorn 子行程
#                (以 RESUME_DB_PATH / RESUME_UPLOAD_DIR 環境變數指向沙盒)
#
# 網頁執行器 POST /api/run-tests 另外再包一層：
#   子行程的 RESUME_DB_PATH / RESUME_UPLOAD_DIR 會被覆寫成
#   tempfile.TemporaryDirectory() 底下的一次性資料夾，執行完即刪除。
#   另外以 RESUME_RUN_TESTS_ACTIVE 標記子行程，避免測試再觸發測試。
